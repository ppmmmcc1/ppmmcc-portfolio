## 0. Mission and non-negotiables

Build `nqlab`: a local, Windows-native Python platform for backtesting intraday NQ/MNQ futures strategies with statistically honest validation, Topstep prop-firm rule simulation, and a batch runner designed to work overnight.

The operator is a mechanical engineering student who day trades NQ on a Topstep 50K Combine, trades roughly 30 to 60 minutes per day around the US cash open, and takes 1 to 2 trades per day. He is comfortable with Python. He is down roughly $4,000 over three years of discretionary trading. The purpose of this platform is to answer one question honestly: **does his strategy have a measurable edge, or not?** A platform that flatters a bad strategy is worse than useless, because it will cost him real money.

### Non-negotiable invariants (also write these to `CLAUDE.md` in the repo root)

1. **No same-bar fills.** An order submitted on the basis of bar N's close can only fill on bar N+1 or later.
2. **Higher timeframes expose only the last fully closed bar.** At 10:07, the 15-minute bar covering 10:00–10:15 does not exist yet. The most recent available 15m bar is 09:45–10:00.
3. **Conservative fill model is the default.** Tier 2 (trade-through) is what gets reported as the headline result. Tier 1 (touch) may only be reported explicitly labeled as an optimistic upper bound.
4. **Every run is logged to the trial ledger**, including runs that error, runs that are abandoned, and every variant generated by the LLM. The Deflated Sharpe Ratio is meaningless without an honest trial count, and the trial count is the only defense against the operator fooling himself.
5. **The LLM never selects strategies, tunes parameters, or computes metrics.** It generates text and proposes hypotheses. All numbers come from code.
6. **The holdout set is never read** except through the single scripted `nqlab holdout` command, which records that it was consumed.
7. **Selection is on parameter plateaus, never on peak Sharpe.**
8. All timestamps stored in UTC. All session logic in `America/Chicago`. Never use naive datetimes.

## 1. Environment

- **OS: Windows.** Plain Windows, not WSL. All paths via `pathlib.Path`. No symlinks. No `nohup`, no `fork`.
- Python 3.11 or 3.12. Use a venv at `.venv`.
- **Multiprocessing gotcha:** Windows uses `spawn`, not `fork`. Every parallel entry point needs an `if __name__ == "__main__":` guard, and worker payloads must be picklable. Strategies must therefore be resolved **by name from a registry inside the worker**, not passed as closures or bound methods. This will silently break if ignored.
- Ollama is installed locally and running at `http://localhost:11434`. Detect available models at startup via `GET /api/tags`; do not hardcode a model name. Prefer an instruct model in the 7B–14B range for text tasks. Degrade gracefully: if Ollama is unreachable, the platform must run fully with all LLM features skipped and a warning logged.
- Target hardware: a laptop. Assume 16 GB RAM. Nothing may require loading more than ~2 GB into memory at once. No Docker, no database server, no cloud dependency.

## 3. Data layer

### 3.1 Source abstraction

Define a `DataSource` protocol with implementations. The operator is starting free and upgrading later, so the upgrade must be a config change, not a rewrite.

```python
class DataSource(Protocol):
    def fetch_bars(self, symbol: str, start: date, end: date, interval: str) -> pl.DataFrame: ...
    def fetch_trades(self, symbol: str, start: date, end: date) -> pl.DataFrame | None: ...
    def capabilities(self) -> SourceCapabilities: ...   # has_trades, has_book, history_start
```

Implementations:

1. **`CsvSource` (primary for v1).** Loads 1-minute OHLCV CSVs from `data/raw/`. The operator will supply free NQ 1-minute data (e.g. the Kaggle "NQ Futures 1min Bar 2022-2025" dataset, roughly 1.05M rows). Write a flexible column mapper configured in YAML, because free CSVs have inconsistent headers and timestamp formats. Validate and normalize to a canonical schema on load.
2. **`YFinanceSource` (fallback/top-up).** `NQ=F` 1-minute, but Yahoo only serves a short recent window and the roll handling is undocumented. Mark its output `provenance="low_confidence"` and make the quality report say so loudly.
3. **`DatabentoSource` (write it fully, leave it inactive).** Dataset `GLBX.MDP3`, schemas `ohlcv-1m`, `trades`, `mbo`. **Always call `metadata.get_cost()` and print the estimate before any download.** Activates when `DATABENTO_API_KEY` is present in the environment. This is the upgrade path and the only source that enables fill-model tiers 3 and 4.

### 3.2 Canonical schema

```
ts_utc (datetime, UTC)  |  symbol (str, e.g. NQZ25)  |  open high low close (f64)
volume (i64)  |  source (str)  |  provenance (str)  |  data_version (str hash)
```

Partition Parquet as `parquet/{schema}/{symbol}/{YYYY-MM}/part.parquet`.

### 3.3 Roll calendar

NQ and MNQ are quarterly: March, June, September, December (H/M/U/Z), cash-settled on the third Friday.

- Build a front-month calendar **by volume**: switch when the next contract's daily volume exceeds the current one's. If per-contract volume is unavailable in the free data, fall back to the CME convention of the Thursday 8 calendar days before expiration, and record which method was used in `data_version`.
- **Simulate each session on unadjusted front-month prices.** The operator never holds overnight, so no adjustment is needed for trading.
- For indicators needing lookback across a roll (1-hour MACD), compute on a **back-adjusted (additive)** series aligned to the same timestamps. Preserve point differences.
- **Never compute volume profile on an adjusted series.** Profile levels are real resting-liquidity prices and adjustment moves them.
- Store all three series (unadjusted, back-adjusted, ratio-adjusted) and make the choice explicit per feature. Any feature that does not declare which series it uses should fail a test.

### 3.4 Quality checks (run on ingest, output a report)

Missing bars inside RTH; zero-volume bars; duplicate timestamps; out-of-range prints (> 10 sigma from a rolling median); prices not on a 0.25 tick grid; session boundary violations; gaps spanning holidays. If two sources are available, cross-check 1-minute bars against trades-rebuilt bars and report disagreements. **A bar that fails quality checks must not silently trigger a trade** — flag it and exclude the session, logging the exclusion.

### 3.5 Holdout lockbox

On first ingest, move the final 6 months of data into `data/holdout/`. Any code path outside `nqlab holdout` that opens that directory must raise. Add a test that asserts this.

## 5. Feature layer

All features are **pure functions of a bar history ending at or before the decision timestamp**. No centered windows, no forward fills from the future.

Required features:

- **Bollinger Bands**: configurable length, multiplier, basis type (SMA/EMA), **stdev type (population vs sample — these differ and must be explicit)**, price source.
- **MACD**: configurable fast/slow/signal, price source. Expose line, signal, and histogram separately.
- **ATR**, **session VWAP** (with configurable anchor), **EMA/SMA**.
- **Volume profile**: build from trades data at 0.25-point bins when available. When only 1-minute bars exist, allocate each bar's volume uniformly across its high-low range and **mark the resulting profile `approximate=True`**. Expose POC, VAH, VAL with a configurable value-area percentage (default 70%) and explicit POC tie-breaking. Support prior-RTH-session, prior-Globex-session, composite-N-day, and developing-today profiles as separate functions.
- **Opening range**: high/low over the first N minutes from the RTH open.

### Higher-timeframe alignment

Resample so each HTF bar is **indexed by its close timestamp**, then join with `merge_asof(direction="backward")` on close timestamps. Support both clock-aligned (10:00, 11:00) and session-aligned (09:30, 10:30) hourly bars as a config flag — they produce materially different signals and the operator has not decided which he uses.

### Lookahead test (mandatory, property-based)

For 200 random timestamps t: compute all features on the full dataset, then compute them on data truncated at t, and assert every feature value at times ≤ t is bit-identical. Use `hypothesis`. **If this test does not exist, the platform is not trustworthy.**

## 6. Engine and fill models

Event-driven loop over 1-minute bars, with optional tick replay for the 09:25–10:45 ET window when trades data is available.

### Order types
Limit, stop, stop-limit, market, and OCO bracket (entry with attached stop and target). Orders carry submit timestamp, price, and an optional expiry in bars.

### Contract specs (hardcode as validated constants, in `config/settings.yaml`)

| | NQ | MNQ |
|---|---|---|
| Tick size | 0.25 | 0.25 |
| Tick value | $5.00 | $0.50 |
| Point value | $20.00 | $2.00 |

**10 MNQ = 1 NQ in exposure.** The report must flag any config using more than 10 micros and state the commission penalty in dollars.

### Cost model (TopstepX, round turn)
MNQ $1.22, NQ $3.78. Configurable. Note in the report: 10 MNQ costs $12.20 versus $3.78 for 1 NQ for identical exposure.

### Slippage model
- Limit orders: zero slippage when filled. The cost is adverse selection and non-fills, captured by the fill tier.
- Stops and market orders: 1 tick default in RTH. 2–4 ticks in the first minute after 09:30 ET, at 08:30/10:00 ET releases, and on FOMC days. Configurable by time-of-day bucket.

### Fill model tiers (implement all four as interchangeable classes)

1. **Touch (optimistic).** Fill if bar low ≤ limit for a buy. **Upper bound only, never the headline.**
2. **Trade-through (DEFAULT).** Fill only if price trades at least one tick through the limit (low ≤ limit − 0.25 for a buy). Approximates "the queue at that price was consumed."
3. **Queue model (requires trades data).** Estimate resting size ahead when the order joined, fill only once cumulative volume traded at that price exceeds the queue ahead, with a configurable cancellation haircut.
4. **MBO replay (requires Databento MBO).** Insert a virtual order, track true queue position. Use on a sample of ~200 sessions to calibrate tiers 2 and 3.

**Every report shows results under all available tiers side by side.** If the edge vanishes between tier 1 and tier 2, the report must say in plain language: *"This strategy's profit comes from the fill assumption, not from the market."*

### Ambiguous bar rule
If a bar touches both stop and target, assume the **stop filled first** unless tick data proves otherwise. Count and report how many trades were resolved by this rule — if it is more than ~15% of trades, the result is not trustworthy at bar resolution and the report must say so.

### Required engine tests
Golden-file tests with hand-computed trade lists. At minimum: a limit that should not fill under tier 2 but does under tier 1; a bracket where both legs are touched in one bar; a position force-flattened at 15:10 CT; a trade spanning the maintenance break.

## 7. Topstep rules layer

Implement as a **stateful layer between strategy and engine**, driven entirely by `config/topstep_50k.yaml`. Never hardcode these numbers — they change.

### Trading Combine 50K (as of late 2026, flag for verification against Topstep's Help Center)

```yaml
account_size: 50000
profit_target: 3000
max_loss_limit:
  amount: 2000
  trails: end_of_day_balance_highs   # never moves down
  locks_at: 50000                     # once EOD balance >= 52000
  enforced: real_time                 # INCLUDING UNREALIZED P&L
daily_loss_limit:
  amount: 1000
  optional: true        # chosen at purchase, carries to funded account, cannot be removed
consistency:
  best_day_max_pct: 0.55   # NOTE: some sources say 0.50. Make configurable, flag in report.
max_contracts: {minis: 5, micros: 50}
flatten_deadline_ct: "15:10"
```

Express Funded Account: MLL starts at −$2,000 from a $0 balance, resets to $0 after first payout. Payout split 90/10, $125 minimum. Standard path requires 5 winning days of ≥ $150 and caps a request at 50% of balance, maximum $2,000. Consistency path requires ≥ 3 trading days with best day ≤ 40%, cap $3,000.

### What the layer must track
Balance, end-of-day high, current MLL level, **real-time equity including unrealized P&L checked at every bar low and high** (or every tick when available), DLL state, contract caps, consistency ratio. On MLL or DLL touch: liquidate at market with slippage, mark account failed or day stopped.

### Combine Monte Carlo (this is the headline output)
Run a simulated Combine starting on **every session in history** (overlapping windows), plus 10,000 bootstrapped trade sequences. Report:

- P(pass), median sessions to pass, P(fail by MLL), P(fail by consistency)
- P(reaching first payout | passed), expected number of payouts before MLL breach
- Distribution of maximum consecutive losses versus the MLL buffer

### The sizing question
Do **not** use Kelly or fixed-fractional on account size. Effective capital is the **distance to the MLL**, which starts at $2,000. Risking 1% of $50,000 means four losses ends the account.

Implement `optimal_risk_search()`: sweep risk-per-trade from 2% to 40% of current MLL buffer and find the value maximizing **P(reaching first payout)**, not expected profit. Plot the curve. These usually peak well below the profit-maximizing size, and the report should show both so the difference is visible.

### Mandatory context line in every Topstep report
> A zero-edge trader passes this Combine roughly 40% of the time (gambler's ruin with a $2,000 floor and a $3,000 target). Passing is weak evidence of skill.

## 8. Validation suite

### 8.1 Walk-forward
Rolling and anchored. Default: optimize on 120 sessions, trade the next 20, roll by 20. Compute **Walk-Forward Efficiency** = annualized OOS return / annualized IS return of the selected parameters. Flag WFE < 0.5. Also report parameter stability across windows — optima that jump wildly are a red flag and should be stated as such.

### 8.2 Combinatorial Purged Cross-Validation
Lopez de Prado's CPCV. N groups of sessions, test on every combination of k, train on the rest, with purging and an embargo. Intraday flat-at-close strategies are nearly independent across sessions so purging matters less, but CPCV still yields a *distribution* of OOS paths rather than one. Use `skfolio`'s `CombinatorialPurgedCV` or a short custom implementation.

### 8.3 Multiple-testing corrections
- **PSR and Deflated Sharpe Ratio** (Bailey & Lopez de Prado 2014). DSR must pull N from the trial ledger automatically. **Require DSR ≥ 0.95.**
- **PBO via CSCV** (Bailey, Borwein, Lopez de Prado, Zhu). Matrix of time-blocks × configurations, all symmetric splits, record the OOS rank of the IS winner. **Require PBO < 0.2.** Above 0.5 means the selection process is worse than random.
- **SPA / StepM** via the `arch` package, fed the daily P&L matrix of every variant tested.

### 8.4 Monte Carlo and synthetic data

| Method | Implementation |
|---|---|
| Trade-order reshuffle | Permute realized trade P&Ls. Gives the drawdown distribution given this edge. **Not a test of edge.** |
| Trade bootstrap | Resample trades with replacement. CI on expectancy, P(final < 0), Combine pass rate. |
| Stationary / circular block bootstrap | `arch.bootstrap.StationaryBootstrap`, `CircularBlockBootstrap`. |
| GARCH simulation | Fit GJR-GARCH with t-errors to 1m or 5m returns **after removing intraday seasonality**, then simulate. |
| Random walk, matched volatility | i.i.d. returns scaled to the U-shaped intraday volatility curve. Sanity floor only. |
| **Masters intrabar-preserving permutation (PRIMARY)** | Decompose each bar into the log gap from prior close plus (high−open, low−open, close−open) in logs. Permute gaps and intrabar tuples **separately and within time-of-day buckets**. Rebuild prices. Volume travels with its bar. |

**MCPT procedure:** run the full strategy *including its optimization step* on real data, record the statistic. Repeat on ≥ 1,000 permuted datasets, **re-optimizing on each**. p ≈ (1 + count(perm ≥ real)) / (1 + n_perm). Require **p < 0.05**, and report where the real result sits in the null distribution, not just the p-value.

**Fill-optimism diagnostic (run this on every strategy):** run on a pure random walk with the strategy's own fill model. A mean-reversion limit strategy with touch fills is often *profitable* on random data. If it is, the report states: *"your fill model is generating this profit, not the market."*

### 8.5 Null calibration harness (build this before trusting anything)
Create deliberately worthless strategies: random entries with the operator's exits, coin-flip direction, fixed-time entry. Run the full validation pipeline. **Assert they are rejected at approximately the nominal rate (~5% false positives at p=0.05).** If the validators pass junk, the validators are broken. Make this a CI test.

### 8.6 Sample size reporting
Every report shows required-N given observed expectancy:

| Expectancy (stdev ≈ 1R) | N for t=2 | N for t=3 |
|---|---|---|
| 0.30R | ~45 | ~100 |
| 0.20R | ~100 | ~225 |
| 0.10R | ~400 | ~900 |
| 0.05R | ~1,600 | ~3,600 |

Also report the standard error of the Sharpe estimate. **One year of daily data gives SE(annualized Sharpe) ≈ 1.0.** Print this next to every Sharpe so it is never read naively. Use t=3 as the bar when the strategy was chosen from a family (Harvey, Liu & Zhu 2016).

## 9. Selection funnel

**This is the core of the platform. Do not build a leaderboard sorted by Sharpe.** With 10,000 coin-flip configs the best will show a Sharpe near 4 by chance alone; the expected maximum Sharpe of N worthless trials grows with sqrt(2·ln N).

```
Stage 0  REGISTER   Strategy FAMILY pre-registered with full param grid declared up front.
                    Configs never compete individually. Writes research_log/<id>.yaml, hashed and locked.
Stage 1  SCREEN     Vectorized pass. Kill negative expectancy under tier-2 fills. Saves CPU, proves nothing.
Stage 2  PLATEAU    Score = MEDIAN Sharpe of the parameter NEIGHBORHOOD, not the max.
                    A lone spike surrounded by losers is noise. Output the heatmap.
Stage 3  WALKFWD    Walk-forward the SELECTION RULE itself ("pick the best plateau from the last 120
                    sessions"), not a fixed parameter set. This is what he will actually do live.
Stage 4  PERMUTE    MCPT re-running the entire selection procedure on synthetic bars. p < 0.05.
Stage 5  DEFLATE    DSR >= 0.95 using honest N from the ledger. PBO < 0.2.
Stage 6  PROPSIM    Topstep Monte Carlo. P(pass), P(first payout).
Stage 7  HOLDOUT    One scripted look. Consumption recorded permanently.
```

**Primary ranking metric: P(reaching first payout), not Sharpe.** Two strategies with identical Sharpe can have very different pass rates depending on where their losing streaks cluster against a trailing drawdown. Report Sharpe, DSR, expectancy in R and dollars, profit factor, max consecutive losses, and P(pass) together — never one alone.

A family failing any gate is **archived, not tweaked**. Tweaking creates a new family with a new pre-registration that joins the trial count. Enforce this in the CLI: `nqlab promote` refuses to advance a failed family.

## 10. Results store and reporting

**DuckDB over Parquet, no server.** Tables:

- `runs`: run_id (hash of strategy+version+params+data_version+fill_model+cost_model+rules_model), git commit, timestamp, status (incl. `errored`, `abandoned`), family_id, origin (`human` | `llm_variant`)

- `trial_ledger`: every run ever, for DSR's N. **Append-only. No deletes.** Add a test asserting no delete path exists.

### HTML report (Jinja2 + Plotly, self-contained single file)
Equity curve with MLL floor overlaid; permutation null distribution with the real result marked; walk-forward segment table; parameter heatmap showing plateau versus spike; results under each fill tier side by side; time-of-day entry breakdown; Topstep outcome distribution; MAE/MFE scatter; the sample-size table with the strategy's position on it; trial count used for DSR.

Open with a **verdict block**: PASS / FAIL / INSUFFICIENT DATA against pre-registered criteria, with the reason in one plain sentence. The operator should be able to read the top of the page and know whether to continue.

## 11. Ollama integration

Client in `src/nqlab/llm/`. All four roles enabled. **Every LLM call is logged with its prompt, response, and model name to `research_log/llm/`.**

### Hard guardrails (encode as assertions, not comments)
- The LLM **never** computes a metric, ranks strategies, or chooses a parameter value. Any numeric output from it is discarded.
- LLM-proposed variants are **auto-inserted into the trial ledger with `origin='llm_variant'` at the moment of generation**, before any backtest runs. This is the critical one: generating 200 variants and keeping the best is industrial-scale p-hacking, and the only defense is that all 200 count toward N in the DSR.
- The LLM cannot read the holdout.
- If Ollama is down, everything else runs.

### Role 1: Spec linter
Input: a strategy YAML spec. Output: a list of undefined, ambiguous, or contradictory parameters as **questions**, checked against the full required-parameter list in section 13. Runs automatically on `nqlab spec lint` and as a pre-commit hook on `specs/`. This is the highest-value role, because the operator's rules are genuinely half-specified.

### Role 2: Losing-trade post-mortem
Input: the N worst trades with context (time of day, realized vol, distance to level, release day flag, HTF state, MAE/MFE). Output: prose describing what they share.

**Mandatory framing in the output:** the result is written to a **new pre-registration draft** in `research_log/hypotheses/`, never applied as a filter to the existing strategy. The prompt must instruct the model to phrase findings as hypotheses to test, and the report must carry the line: *"An LLM will always find a pattern, including in pure noise. This is a hypothesis, not a finding."*

### Role 3: Variant generation
Input: a strategy template plus the family's parameter space. Output: N structured variant specs. Ledger them at generation time. Cap N per session via config (default 20) so the trial count cannot explode unnoticed, and print the resulting DSR penalty before running them.

### Role 4: Morning summary
After an overnight batch, the LLM reads **metrics the code computed** and writes a plain-English summary: what ran, what passed, what failed and why, what is worth looking at. Zero statistical risk since it narrates numbers rather than producing them. Writes `reports/morning_<date>.md`.

## 12. Overnight batch runner

**SQLite-backed job queue.** Jobs: `{job_id, type, payload_json, status, attempts, checkpoint_json, created, started, finished}`.

Requirements:
- **Checkpointing.** A 1,000-permutation MCPT writes progress every 25 permutations. A crash or a closed laptop lid resumes from the checkpoint rather than restarting.
- Dependency ordering (permutation runs after the sweep it depends on).
- Parallelism via `joblib` with the Windows spawn guard, defaulting to `cpu_count - 1`.
- Memory ceiling per worker; stream from Parquet rather than loading full history.
- Crash isolation: a failed job is logged as `errored` **in the trial ledger** and the queue continues.
- Writes `reports/overnight_<date>/` with the HTML reports plus the LLM morning summary.

`scripts/run_overnight.bat`:
```bat
@echo off
cd /d %~dp0\..
call .venv\Scripts\activate.bat
python -m nqlab.cli run-queue --workers auto --log reports\overnight_%DATE:~-4%%DATE:~4,2%%DATE:~7,2%.log
```
Document Windows Task Scheduler setup in the README, and include the power settings needed so the laptop does not sleep mid-run.

## 13. Strategy specs

Specs live in `specs/*.yaml`, are versioned, hashed into the run_id, and must declare **every** parameter below. The spec linter fails on any omission.

### 13.1 The operator's current strategy — INCOMPLETE BY DESIGN

Scaffold `specs/bb_vp_macd.yaml` with every field present and explicitly marked `REQUIRED_UNDECIDED` where he has not chosen. **Do not invent defaults for these.** The platform should refuse to run until they are filled, and the linter should list them as questions.

**Context filters (15m and 1h MACD):**
- Definition of "direction": MACD line vs signal? Histogram sign? Line vs zero? EMA slope?
- MACD params per timeframe (12/26/9?) and price source (close vs HLC3)
- Hourly bars clock-aligned or session-aligned? (materially different signals)
- Agreement rule: both HTFs must agree, either, or does 1h dominate?

**Bollinger extremes:**
- Band timeframe (1m or 5m?), length, multiplier, basis SMA or EMA, **stdev population or sample**, price source
- Does the resting order **reprice each bar** as the band moves, or freeze at signal-time band value?

**Volume profile:**
- Source: prior RTH, prior Globex, composite N-day, or developing today?
- Value area % (70?), bin size (0.25 or aggregated), POC tie-breaking
- Built from trades (correct) or bars (approximate)?
- "Aligned" = band within X ticks of POC/VAH/VAL. **What is X?**
- Which levels qualify for longs vs shorts?
- Order price: the band, the level, or the better of the two?

**Trigger (1m/5m MACD cross):**
- Is the cross the **entry trigger** (then it is a stop/market entry, not a resting limit) or a **confirmation** that must precede the limit fill within N bars? **These are different strategies — scaffold both and test separately.**
- Cross definition, minimum histogram magnitude
- Must both 1m and 5m cross, within what window?

**Order management:**
- Time window (09:30–10:30 ET?), order expiry in minutes, cancel if band moves > M ticks
- Max concurrent positions, max trades per day, stop-after-first-win/loss rule
- Stop: fixed ticks, ATR multiple, or beyond next profile level + buffer?
- Target: opposite band, basis, POC, fixed R? Partials? Breakeven move and when?
- Time stop (flatten at 10:30/11:00 ET?)
- Skip days: FOMC, 08:30 ET releases, half days, roll week?

**Sizing:** NQ or MNQ, risk per trade in dollars and as % of MLL buffer, daily stop.

### 13.2 Baseline strategies (build these FIRST, before his)
These are the benchmarks his strategy must beat. If it cannot beat a random-entry baseline, that is the finding.

1. **ORB 5/15/30 minute** on NQ from the RTH open.
2. **First-half-hour momentum**: sign of the 09:30–10:00 ET return, traded in the following window.
3. **Random entry** with his exit logic, at matched trade frequency.
4. **Buy and hold the session** (open to close).

### 13.3 Discretionary parity check
Build `nqlab parity label`: the operator hand-labels 20 to 30 historical sessions ("I would have taken this trade here"). The platform compares coded signals against his labels and reports precision/recall plus a diff of divergences. Where they diverge he must decide explicitly which version is being tested. **This is the step that catches "the code isn't testing what I actually do."**

Also build `nqlab parity import`: ingest TopstepX trade history CSV, align to model predictions, report fill-rate difference, slippage difference, and expectancy difference with confidence intervals. Once live, this is the highest-value feature in the platform, because it is the only thing that catches a fill model that is quietly lying.

## 16. Self-review loop

After reaching the end of section 15, **do not stop**. Run this loop until the definition of done is met or you genuinely cannot improve further:

1. **Review as a senior quant engineer reviewing a junior's work before it touches real money.** Write the review to `reviews/review_<n>.md`. Be specific and harsh. Cite file and line.
2. Check specifically for:
   - **Lookahead leaks.** Re-derive by hand, do not trust the test alone. Check HTF joins, volume profile construction, roll boundaries, any `shift()`.
   - **Silent optimism.** Anywhere a default makes results look better: fill assumptions, cost omissions, ambiguous-bar handling, excluded bad sessions quietly dropped.
   - **Trial ledger leaks.** Any code path producing a result that does not get counted.
   - **Windows-specific breakage.** Spawn-safety, path separators, file locking, long paths.
   - **Statistical correctness.** Is the permutation re-optimizing? Does DSR pull the real N? Is CPCV purging correctly?
   - **The operator fooling himself.** Can he accidentally promote a failed family? Peek at the holdout? Re-run until something passes?
   - Memory ceilings, error handling, dead code, missing tests.
3. For each finding, write down **two or more** candidate fixes with tradeoffs, pick the best, justify in one sentence.
4. Apply the fixes. Re-run the full test suite plus the null calibration harness.
5. Repeat. Each review should find materially less than the last. Stop when a full pass produces only cosmetic findings.

## 18. Final note to the reviewing model

The failure mode here is not a crash. It is a platform that runs beautifully and tells a 21-year-old that a strategy works when it does not, which costs him money he does not have and years he will not get back. Every ambiguous default should resolve pessimistically. Every uncertain result should read INSUFFICIENT DATA rather than PASS. If a tradeoff pits convenience against statistical honesty, honesty wins without discussion.
